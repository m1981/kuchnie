## 1. kitchen-app — Web Sales Tool

### What the Brief Says You Need

> "Predefined 2.5D layouts + decor picker + 2.5D preview with Kronospan/Egger textures"

### What Actually Exists

| Feature | Status | Reality |
|---------|--------|---------|
| 2D plan view canvas | ✅ Works | CSS-positioned boxes on a grid canvas — not 2.5D, just flat 2D |
| Cabinet CRUD (add/delete/move) | ✅ Works | Base, Wall, Tall + 13 equipment presets |
| Cost estimation (BOM system) | ✅ Works | Full recipe-based BOM with hardware rules, purchasing strategies, waste factors |
| Material picker (Egger/Krono/Forner/Cleaf) | ✅ Works | 20 materials in catalog, per-cabinet overrides |
| Admin panel (materials/hardware/rules) | ✅ Works | Full CRUD for materials, hardware sets, hardware rules |
| Cost trace panel | ✅ Works | Transparent calculation breakdown with formulas |
| Carpenter's heuristics | ✅ Works | Auto-corrects door counts, warns about drawer widths, shelf sag, board sizes |
| **2.5D preview with textures** | ❌ **MISSING** | The UI renders flat CSS boxes with no textures, no perspective, no material visualization |
| **Kronospan/Egger texture rendering** | ❌ **MISSING** | Materials are just names in a dropdown — no visual representation |
| **Predefined layout templates** | ⚠️ Partial | Only one hardcoded "IKEA-style" reference layout. No template library |
| **L-shape / U-shape / galley support** | ❌ **MISSING** | The layout engine only supports a single straight row (base + wall). No turns, no corners, no multi-wall |
| **Customer project management** | ❌ **MISSING** | Single hardcoded project ("Smith Family Kitchen"). No create/save/load/switch |

### Key Source Files

- `kitchen-app/kitchen_app/state.py` — `KitchenState` with all reactive state, layout logic, cost calculation
- `kitchen-app/kitchen_app/kitchen_app.py` — Reflex UI components (canvas, sidebar, cost trace)
- `kitchen-app/kitchen_erp/bom_generator.py` — Recipe-based BOM tree builder
- `kitchen-app/kitchen_erp/rules_engine.py` — Tag-based hardware rules (hinges, handles, legs, etc.)
- `kitchen-app/kitchen_erp/models.py` — SQLModel database models (Material, Cabinet, Project, HardwareSet)
- `kitchen-app/kitchen_erp/purchasing.py` — 4 purchasing strategies (sheet, linear, countertop, exact)
- `kitchen-app/kitchen_erp/recipes.json` — Cabinet type definitions with dimension formulas

### Critical Gaps

1. **No visual rendering** — The customer sees colored CSS boxes, not a kitchen preview. The krono-compositor exists separately but is NOT connected to kitchen-app.
2. **Single straight row only** — No L-shape, U-shape, or galley. The `_relayout_project()` method only handles one base row and one wall row on a single X axis.
3. **No project persistence** — Can't save multiple customer projects. Single SQLite DB, single project.

## 2. kitchen-plugin — Blender 3D Generator

### What the Brief Says You Need

> "2D layout editor → intermediate format (JSON/YAML) → Blender backend reads intermediate → applies Kronospan/Egger textures → generates renders"

### What Actually Exists

| Feature | Status | Reality |
|---------|--------|---------|
| JSON config parser | ✅ Works | Full validation, defaults, settings |
| Domain model (Wall, Room, Cabinet, Layout) | ✅ Works | Proper DDD with Vector2D/3D, Transform2D, BoundingBox |
| Layout engine (I/L/U shapes) | ✅ Works | Turns, corners, wall-relative positioning |
| Blender geometry builder | ✅ Works | Carcass boards (side/top/bottom/back), door/drawer fronts with gaps, fillers, countertops |
| Construction parameters | ✅ Works | 18mm corpus, 3mm HDF back, groove offset, front gaps |
| Geometry manifest (JSON) | ✅ Works | Full export with local/world bounds, dimensions, validation |
| Manifest validator | ✅ Works | Dimension checks, overlap detection, vertex/face counts |
| Wireframe rendering | ✅ Works | Auto camera/lighting setup |
| Material application | ⚠️ Basic | Creates Blender materials with colors from config, but no PBR textures, no Kronospan/Egger materials |
| **Config editor (2D layout UI)** | ❌ **MISSING** | Configs are hand-written JSON files. No GUI editor |
| **Kronospan/Egger PBR textures** | ❌ **MISSING** | Materials are flat RGB colors, not real laminate textures |
| **Photorealistic rendering** | ❌ **MISSING** | Only wireframe rendering. No Cycles/EEVEE photorealistic output |
| **Export to customer format** | ❌ **MISSING** | Exports .blend and wireframe PNG — not customer-facing quality |
| **Connection to kitchen-app** | ❌ **MISSING** | No way to import a kitchen-app layout into kitchen-plugin |

### Key Source Files

- `kitchen-plugin/src/main.py` — CLI entry point, full pipeline orchestration
- `kitchen-plugin/src/config_parser.py` — JSON config loader with validation
- `kitchen-plugin/src/wall_builder.py` — Config-to-domain adapter (Wall, Room, Cabinet, Layout)
- `kitchen-plugin/src/geometry_builder.py` — Blender mesh creation (carcass, doors, drawers, fillers, countertops)
- `kitchen-plugin/src/geometry_manifest.py` — JSON manifest export with validation
- `kitchen-plugin/src/manifest_validator.py` — Dimension/overlap/vertex validation
- `kitchen-plugin/src/validators.py` — Config validation (widths, gaps, corners, room fit)
- `kitchen-plugin/src/kitchen/` — Domain model (cabinet.py, layout.py, wall.py, standards.py, cabinet_geometry.py)
- `kitchen-plugin/configs/ref_i_shape.json` — Reference I-shape config

### Critical Gaps

1. **No visual texture pipeline** — The Blender builder creates correct geometry but with placeholder colors. The krono-compositor has the texture swapping logic but works with pre-rendered scenes, not live Blender scenes.
2. **No GUI** — Configs must be hand-edited JSON. No drag-and-drop, no visual feedback.
3. **No connection between kitchen-app and kitchen-plugin** — They use completely different data models. kitchen-app has `Cabinet` (SQLModel with module_kind, x_mm, y_mm). kitchen-plugin expects JSON config with runs/base/upper arrays.

### What the Brief Says You Need

> "CLI tool #1: cut list CSV → e-rozrys / e-rozkroj. CLI tool #2: System32 drilling data → DXF for CNC company. Cost estimation with nesting results."

### What Actually Exists

| Feature | Status | Reality |
|---------|--------|---------|
| Panel calculator (7 cabinet types) | ✅ Works | base_door, base_drawer, corner_blind, corner_internal, sink, cargo, oven |
| System 32 drilling | ✅ Works | 32mm raster, shelf pin holes with configurable offsets |
| Hinge cup drilling | ✅ Works | Blum CLIP top 35mm default, configurable |
| Handle drilling | ✅ Works | Configurable spacing, position |
| Edge banding per side | ✅ Works | Each panel knows which edges get banding |
| Cutting CSV (semicolon-delimited) | ✅ Works | id, role, width, height, thickness, material, quantity, edges |
| Edging CSV | ✅ Works | panel_id, edge, length_mm, material |
| Legrabox DXF generator | ✅ Works | Full DXF with System32 holes, profile holes, dowels, edge marks |
| **CSV format for e-rozrys/e-rozkroj** | ⚠️ Unknown | The CSV is semicolon-delimited (Polish standard) but format compatibility unverified |
| **System32 DXF for all panels** | ❌ **MISSING** | DXF only exists for Legrabox side panels. No DXF export for general panel drilling |
| **Nesting optimization** | ❌ **MISSING** | No nesting/cutting optimization. Just raw panel list. Feed CSV into e-rozrys for that |
| **Cost estimation from nesting** | ❌ **MISSING** | kitchen-cad has no cost calculation at all. Costing lives in kitchen-app's BOM system |
| **Connection to kitchen-plugin** | ❌ **MISSING** | kitchen-cad uses its own `CorpusSpec` model. kitchen-plugin uses JSON config. No bridge |
| **Connection to kitchen-app** | ❌ **MISSING** | kitchen-app's `Cabinet` (SQLModel) has no way to export to `CorpusSpec` (Pydantic) |
| **CNC-ready DXF for general drilling** | ❌ **MISSING** | Only Legrabox-specific DXF. No generic DXF with System32/hinge/handle holes for any panel |

### Key Source Files

- `kitchen-cad/src/kitchen_cad/models.py` — Full cabinet engineering data model (28 classes, enums for all types)
- `kitchen-cad/src/kitchen_cad/panel_calculator.py` — Cutting list generator for all 7 cabinet types
- `kitchen-cad/src/kitchen_cad/drill_engine.py` — CNC drill point calculator (System32, hinges, handles, shelf pins)
- `kitchen-cad/src/kitchen_cad/csv_generator.py` — Semicolon-delimited CSV export (cutting + edging)
- `kitchen-cad/generators/legrabox_side_panel.py` — DXF generator for Blum Legrabox side panels
- `kitchen-cad/example_generate.py` — Demo with 5 cabinets, generates CSV output

### Critical Gaps

1. **No bridge between kitchen-cad and anything else** — It's a standalone tool that requires you to manually define `CorpusSpec` objects in Python code. There's no import from kitchen-app or kitchen-plugin.
2. **No general DXF export** — The brief says "DXF files to CNC company" but only Legrabox side panels have DXF. General panels get CSV only.
3. **No nesting integration** — The brief mentions "Cost estimation refines with real nesting results" but there's no nesting feedback loop.

## 5. The Integration Gap — The Biggest Problem

The brief describes a pipeline:

```
kitchen-app → kitchen-plugin → Blender → kitchen-cad
                                        → krono-compositor
```

**Reality: All four systems are completely independent.** There is NO data flow between them.

### Data Model Incompatibility

| System | Data Model | Key Types |
|--------|-----------|-----------|
| kitchen-app | SQLModel (ORM) | `Cabinet` (module_kind, x_mm, y_mm, door_count, drawer_count), `Project`, `Material` |
| kitchen-plugin | JSON config dict | `{runs: [{label, base: [{type, width}], upper: [...]}], settings: {...}}` |
| kitchen-cad | Pydantic | `CorpusSpec` (width, height, depth, config: CabinetConfig), `Panel`, `DrillPoint` |
| krono-compositor | JSON dict | `{cabinets: [{width_mm, height_mm, depth_mm, type, id_hex, handle}]}` |

**Four incompatible data models. No shared schema.**

### Missing Connections

| Connection | Status | What's Missing |
|-----------|--------|----------------|
| kitchen-app → kitchen-plugin | ❌ | kitchen-app's `Cabinet` model can't export to kitchen-plugin's JSON config format |
| kitchen-app → krono-compositor | ❌ | kitchen-app never calls the compositor API |
| kitchen-plugin → kitchen-cad | ❌ | kitchen-plugin's JSON config can't export to kitchen-cad's `CorpusSpec` model |
| kitchen-plugin → krono-compositor | ❌ | gen_kitchen.py is a standalone script, not driven by kitchen-plugin's output |
| kitchen-cad → kitchen-app | ❌ | No nesting results feed back into cost estimation |

### The Missing "Intermediate Format"

The brief explicitly calls for an **intermediate format** as the hub. What exists:

- kitchen-app uses SQLModel (`Cabinet`, `Project`, `Material`)
- kitchen-plugin uses JSON config (`runs/base/upper` with cabinet dicts)
- kitchen-cad uses Pydantic (`CorpusSpec`, `Panel`, `DrillPoint`)
- krono-compositor uses JSON (`layout.json` with cabinets array)

No shared schema. No export/import adapters. Each system is an island.

## 7. Priority Gaps to Close

Ordered by impact on the pipeline:

### 1. ✅ The Intermediate Format — DONE

Schema implemented in `schemas/` with **layered architecture**.

**Key design decision: kitchen-app knows nothing about construction.**

```
Layer 1 (Sales):   kitchen-app writes layout + materials + pricing
Layer 2 (3D):      kitchen-plugin enriches with construction params
Layer 3 (CNC):     kitchen-cad enriches with hardware specs
```

kitchen-app only specifies: layout template (I/L/U), cabinet types + widths, material IDs, pricing rules.
Heights, depths, construction, hardware, drilling — ALL derived by downstream tools from European standards.

Files:
- `schemas/kitchen-design.schema.json` — JSON Schema
- `schemas/kitchen_design.py` — Pydantic model with adapters
- `schemas/example_design.json` — L-shape kitchen example (Layer 1 only)
- `schemas/README.md` — Full documentation

Tested: validation, plugin config export, CorpusSpec export for all cabinet types. Layer 1 size ~2KB.

### 2. kitchen-app → kitchen-plugin Bridge

Export kitchen-app's `Cabinet` list to kitchen-plugin's config format. This connects sales to 3D.

- Add an "Export to Blender" button in kitchen-app
- Adapter function: `Cabinet` (SQLModel) → JSON config dict
- Call kitchen-plugin's `main.py` with the exported config

### 3. kitchen-app → krono-compositor Bridge

Call the compositor API from kitchen-app to show material previews.

- Add a "Preview" button in kitchen-app sidebar
- HTTP POST to krono-compositor `/api/v1/render` with zone config
- Display returned JPEG in the UI

### 4. kitchen-plugin → kitchen-cad Bridge

Export kitchen-plugin's cabinet definitions to kitchen-cad's `CorpusSpec` format.

- Adapter: JSON config cabinet dict → `CorpusSpec` with appropriate `CabinetConfig` variant
- Generate cutting CSV + drill data automatically from kitchen-plugin output

### 5. Multi-Wall Layout in kitchen-app

The web app only supports straight runs. Add L/U shape support.

- Add turn direction to run model
- Implement `_relayout_project()` with wall-relative positioning (like kitchen-plugin's LayoutEngine)
- Update canvas rendering for multi-directional layouts

### 6. DXF Export for All Panels

The CNC shop needs DXF, not just CSV. Extend the Legrabox DXF generator.

- Generalize `legrabox_side_panel.py` to work with any panel
- Add System32, hinge cup, handle holes to DXF output
- One DXF per panel, or batch DXF with all panels

### 7. Real Texture Assets

Source Kronospan/Egger laminate textures for the compositor.

- Download high-res textures from manufacturer websites
- Store in `assets/textures/` matching catalog IDs
- Add texture preview to kitchen-app material picker

## Appendix: System Architecture (Current State)

```
┌─────────────────────────────────────────────────────────────┐
│                     kitchen-app (Reflex)                     │
│  2D canvas + cabinet CRUD + BOM costing + admin panel       │
│  Data: SQLModel (Cabinet, Project, Material)                 │
│  Output: SQLite DB (no export)                               │
└─────────────────────────────────────────────────────────────┘
        ✗ (no connection)
┌─────────────────────────────────────────────────────────────┐
│                  kitchen-plugin (Blender)                     │
│  JSON config → domain model → Blender geometry → manifest    │
│  Data: JSON config dict + domain types                       │
│  Output: .blend, wireframe PNG, JSON manifest                │
└─────────────────────────────────────────────────────────────┘
        ✗ (no connection)
┌─────────────────────────────────────────────────────────────┐
│                   kitchen-cad (Python CLI)                    │
│  CorpusSpec → panels → drill points → CSV + DXF             │
│  Data: Pydantic (CorpusSpec, Panel, DrillPoint)              │
│  Output: cutting CSV, edging CSV, Legrabox DXF               │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│              krono-compositor-mvp (FastAPI)                   │
│  Blender scene → multi-pass renders → OpenCV compositing    │
│  Data: layout.json (hardcoded) + texture files (missing)     │
│  Output: composited JPEG via POST /api/v1/render             │
└─────────────────────────────────────────────────────────────┘
```

All four systems are **fully functional in isolation** but **completely disconnected from each other**.
