## 🟠 Cross-Feature Mismatch #1 — `material_refs` Structure (F002 vs F003/F005)

### F002 spec, Q5 (line 306):

> "F005 (`MaterialResolver`) takes a `CabinetInstance.material_refs: {"body": "kronospan_u112_pm", "front": "egger_h3303_st10", ...}` and a `material_role: "body"`, returns the concrete material."

This says `material_refs` maps `role → decor_id` directly.

### F003 spec, line 307 (instantiation example):

> `cabinet.material_refs = {body: "project_body", front: ..., ...}`

This says `material_refs` maps `role → slot_name`.

### F005 spec, line 201 (glossary impact):

> "`MaterialRef` — promote placeholder → concrete. **Refined meaning:** in v1.0, `material_refs` on `CabinetInstance` is a `dict[role_str, slot_name_str]`. The slot name is a project-level identifier (e.g., `project_body`); the resolver chains to the decor."

This locks in `role → slot_name`.

### What's right

F003 and F005 are consistent and correct. The three-stage chain (`role → slot → decor`) is the explicit architectural decision in F005 ADR.

### What's wrong

**F002's Q5 is stale.** It was written before F005's chain design was finalized. The Q5 answer uses concrete decor IDs as values; the actual contract uses slot names.

### Impact

If an F002 implementer reads only F002 and writes `material_refs: dict[str, str]` thinking values are decor_ids, every subsequent feature breaks:
- F003's `material_role_defaults` produces wrong values.
- F005's `resolve_role()` chain fails (treats decor_id as slot_name).
- F008's exporters get confusing data.

### Fix

Edit `features/F002-recipe-engine/spec.md` Q5 to:

> **Q5:** Where does `material_role` get resolved to a concrete `Decor`? → **A:** Not here. F005 (`MaterialResolver`) walks the chain `material_role → project_slot → decor`. A cabinet's `material_refs` maps `{role: slot_name}` (e.g., `{"body": "project_body"}`); the kitchen's `material_slots` then maps `{slot_name: decor_id}` (e.g., `{"project_body": "kronospan_u112_pm"}`). F005 owns the full chain. F002 emits the role string verbatim on each `Panel`.

## 🟠 Cross-Feature Mismatch #2 — Edge Material Roles Undefined

### F002 worked recipe example uses:

```yaml
edges:
  front: front_color
  rear:  body_color
```

### F002 glossary impact says:

> `MaterialRef` — gains a notion of material role strings (`"body"`, `"front"`, `"back"`, `"shelf"`, `"front_color"` for edges)

### F005's canonical role list (spec.md, line 129):

> "warn if a role string isn't recognized (`body`, `front`, `back`, `shelf` are canonical for v1.0)"

### F005 does **not** mention `front_color` or `body_color`.

### What this leaves ambiguous

- Are `front_color`/`body_color` separate slots in `kitchen.material_slots`?
- Or are they "edge banding follows the paired_edge of the front/body decor"?
- The carpentry-correct interpretation is the second (edge of a panel's front matches the front-decor's paired edge, for visual continuity), but neither F002 nor F005 says so.

### Impact

F008's cut-list exporter has to populate edge banding columns. If it doesn't know how to resolve `front_color` to a concrete edge, it either:
- Adds another slot to `kitchen.material_slots` (breaking F005's clean chain), or
- Looks up `paired_edge_id` of the slot whose name shadows `_color` (under-specified), or
- Silently emits empty edge columns (worst).

### Fix

Decide explicitly. Recommend:

> **Edge role convention:** `<material_role>_color` means "use the paired edge of the decor in slot `material_role`". So `front_color` = "edge paired with the decor in slot `project_front`". The resolver provides this via `ResolvedMaterial.paired_edge_id` already; the exporter looks up `resolver.resolve_role("front", cabinet).paired_edge_id`.

Add to F005 spec § Glossary Impact, refine `MaterialRef` to document the `_color` suffix convention. Add F005 LLM Hint: "When asked 'what is `front_color`?' → it's the paired edge of the `front` role's decor. Not a separate slot."

Add to F008 spec § Acceptance Criteria: "Cut list edge columns resolve via `_color` suffix convention; assert `front_color` → paired edge of the front decor."
